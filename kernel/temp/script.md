I'm working towards porting the PBP kernel to C.

I've reached the stage where I need to parse the JSON file generated by das2json from kernel.drawio.

In the Python, Javascript and Lisp versions, I simply used exising JSON libraries.

In looking at the JSON for this use-case, I see that it is fairly regular and I'm thinking that it might be better to simply write a parser customized for this use case, then make it work in Python and again for the other languages, especially the C version. Maybe buying in a whole, generalized JSON parsing library is overkill?

This parser doesn't need to be highly optimized. It is only going to parse relatively small JSON files, all of which are machine generated and are highly regular. It only needs to build lists of key-value objects, like a subset of objects supported by more generalized JSON.

I currently believe that writing this simple parser out in code form is going to result in a simpler C port of the whole PBP kernel. We'll see.

Here's a sample JSON file generated by the das2json tool for kernel.drawio.

The file contains an array of one or more diagrams. A diagram is an object containing four key-value pairs, "name", "children", "connections" and "file".

The most complicated object in this generated JSON file is a wire, one of the objects contained in the "connections" array.

A wire consists of several key-value pairs, "dir", "source", "source_port", "target" and "target_port". 

As it stands, the most common kind of wire is the "across" wire, from child part to another child part. This kind of wire needs all five kv pairs. 

For downward connections (from input gate of a Container part to any of it's children parts) we leave out the "source" port, since that is known to be the equivalent of "self", the Container itself.

"Target" is left out for upward connections. 

For "through" connections" - the most uncommon kind of wire - both "source" and "target" are missing.

---- regarding use of "deref" parameter (part 14)

In C, we can deal explicitly with pointers. Many languages hide pointers from us.

For the C Port of the PBP Kernel project, the explicit handling of pointers adds a new twist. We need to know when to dereference a pointer and when to simply leave it alone.

After struggling with this issue for a while, I've found that the grammar rule "PrimaryIndexed" might hold a key. In some cases we know that the C emitter will call a function, in which case we want to pass the argument as a pointer, whereas in some other cases, like accessing a field of a struct, we want to dereference the pointer. 

C has a shorthand for this kind of dereferencing, the arrow operator, but, we don't need to use it - the emitted code is somewhat uglier than when using the shorthand, but, we don't care, since the generated code is machine-generated and we care less about human readability and writeability at this point.

We want to dereference pointers in other contexts, like array access and slices, but, for simplicity we'll just ignore those use-cases for now. I know from experience that procrastination usually can be resolved later with brainstorming based on what already works up to that point.

So, in the C emitter, "emitc.rwr", I create a parameter and call it "deref". 

I initialize it to false.

I explicitly set it to True or False in the PrimaryIndexed rule. And then pass this value to the support function "getmaybederef" whenever I hit a primary identifier in the Atom rule. I ignore deref in cases of hitting string and number atoms.

As an example of the generated code, let's look at the code generated for the "create_down_container" function in "container.c"

The parameter "proto_conn" is passed in as a pointer to a Wire struct.

When we call "lookupstring", we pass "proto_conn" as an argument without dereferencing it.

We create a local variable "connector" which is also a pointer to a Wire struct.

In the code, we assign to the ".receiver" field. Here, we need to dereference the pointer.

If we look at the rwr code, we see that PrimaryIndexed_lookupstring calls a function. It first sets the deref parameter to False.

In the rule PrimaryIndexed_fieldident, though, we set the deref parameter to True which causes the Atom rule to give us back a string of C code that dereferences the identifier. 

This is what we want and seems to work.

--- re. 3 cell cons cell

Here's something I'm going to try out.

I find that a list data structure is quite flexible.

It could be more efficient, but we don't need to care about efficiency here. We are only building a tool here - the C code emitter - which will only be used during development. The goal is to speed up development and to cut corners where possible. We don't need speed nor size optimization like in production code, we simply need something that will help us work faster.

In Lisp, lists are made of CONS cells with two parts. The first part, traditionally called CAR, then later simply called FIRST, holds a pointer to an item. The second part, traditionally called the CDR and now REST is essentially a pointer to the NEXT cell in the list. If it's the end of the list, the CDR is NIL. Sometimes, we can fit small immediate items, like integers directly into the CAR part instead of using a pointer.

For this specific application, we don't need to optimize the CAR in this way, the CAR will always hold a pointer to either a KV cell or an Object cell. I might wish to optimize KV cells like that in a very few cases, though.

The problem with a 2-part CONS cell is that a generalized garbage collector is needed to reclaim unused CAR items.

A specialized garbage collector needs to know the kind of item that is in the CAR of the cell and how to reclaim it.

Instead of insisting that every item be derived from some kind of class, I'm going to try to add a third field to the CONS cell, which holds a pointer to a reclaim function. If the pointer is NULL, then the item does not need to be reclaimed, like an immediate integer value stored in the CAR. As I said earlier, I'm not going to need immediate values in list cells, but when I get to KV cells there is one use-case - the direction kind of KV - that I might want to insert immediate integer values into the cells.

So, to reclaim a list cell, I intend to call the reclaim function and give it the pointer to the CAR item as a parameter. Then, simply NULL out the list cell and put the list cell back onto a free list.

This might not be the most efficient approach, maybe later I'll want to create classes for items that include procedures for reclamation, but I'll stick with this dynamic approach and see where it leads.

I will define Object and KV cells in a similar way.
